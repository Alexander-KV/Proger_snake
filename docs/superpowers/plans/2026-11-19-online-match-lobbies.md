# План реализации онлайн-матчей и лобби

> При реализации по задачам использовать `superpowers:executing-plans` или
> `superpowers:subagent-driven-development`. Выполненные шаги отмечать в списке.

**Цель** — дать командам в одной локальной сети создать матч, присоединиться и дождаться запуска в общем лобби.

**Архитектура** — FastAPI хранит матчи и участие в SQLite. React использует текущую сессию и получает актуальный список и состав по HTTP. Рекомендуется опрос раз в 3 секунды. Общий канал игровых кадров пригодится на втором этапе.

**Стек** — React, TypeScript, Vite, Tailwind CSS, FastAPI, SQLModel, SQLite и pytest.

**Спецификация** — [онлайн-матчи](../specs/2026-11-19-online-matches-design.md).

## Ограничения

- Первый этап включает форму создания, список матчей, лобби, статичное тренировочное поле, чтение правил и документации, выход участника и закрытие лобби организатором. Панель запуска, отсчёт, игровой раунд и редактор относятся к последующим этапам.
- Матч рассчитан на 2, 3 или 4 команды, по умолчанию 2. Квадратное поле имеет сторону 16, 24 или 32 клетки, по умолчанию 24. Начальная роль — «Организатор-наблюдатель». Организатор в роли игрока занимает место.
- Одна команда может находиться только в одном незавершённом матче в любой роли. Новые команды допускаются только до запуска и при свободном месте. До запуска участник может выйти и сразу освободить место.
- Первая версия принимается в локальной сети. Защищённые экраны используют действующую сессию. Идентификаторы в коде на английском, интерфейс и документация на русском.
- Коммиты создавать при отдельном запросе пользователя. Перед каждым коммитом выполнять форматирование и обязательные проверки по `AGENTS.md`.

## Особые случаи для проверки

- Потерян ответ сервера на создание. Повтор с тем же ключом возвращает исходный ID.
- Две вкладки одной команды подключаются в разные лобби. Создаётся ровно одно участие.
- Две команды претендуют на последнее место. Обновлённый счётчик не превышает вместимость.
- Организатор закрывает лобби, пока другая команда присоединяется. Закрытый матч освобождает все связи независимо от порядка запросов.
- Участник открывает правила, теряет связь или сессию. Его место сохраняется, экран восстанавливается после обновления данных или входа.

### Контракт HTTP первого этапа

| Запрос | Тело и успешный ответ |
| --- | --- |
| `GET /api/matches` | `200 MatchList` с `current_match_id: number \| null` и `matches: MatchSummary[]`. |
| `GET /api/matches/{id}` | `200 MatchLobby` со сводкой, `organizer: TeamLabel`, `participants: TeamLabel[]` и `my_role: MatchRole`. |
| `POST /api/matches` | `{capacity, board_size, organizer_role, request_id}`. Ответ `201 {id}`, при повторе той же попытки `200 {id}`. |
| `POST /api/matches/{id}/join` | `200 {id}` для нового и существующего участия в этом матче. |
| `POST /api/matches/{id}/leave` | `204` после выхода участника из ожидающего матча. Повтор для уже покинутого лобби возвращает `204` и сохраняет участие в другом матче. |
| `POST /api/matches/{id}/close` | `204` после закрытия ожидающего матча организатором. Повтор для того же организатора безопасен. |

`MatchSummary` содержит `id`, `capacity`, `board_size`, `participant_count`, `status`.
`TeamLabel` содержит `id` и `name`. `MatchRole` использует значения из таблицы участия.
`organizer_role` при создании принимает `organizer_observer` или `organizer_player`.
Для конфликтов `409` JSON содержит `detail.code` и `detail.message`; для
`active_match` добавляется `detail.match_id`. Коды конфликтов — `active_match`,
`match_full`, `match_not_waiting`, `request_id_reused`. Некорректные параметры
возвращают `422`. `request_id` состоит из 32 шестнадцатеричных символов.

Проверить `200` и `409 match_full` на последнем месте, один успех и `409 active_match` при входе в разные лобби одной команды, а также отсутствие активного участия после гонки закрытия и входа. - [ ] Запустить `uv run --project backend --locked python -m pytest backend/tests/test_matches.py`. До реализации новые операции возвращают `404`.
- [ ] Реализовать четыре `POST` из контракта. Допустимые параметры проверяются на сервере. Каждая операция захватывает блокировку записи SQLite (`BEGIN IMMEDIATE`) перед чтением состояния и выполняет проверку и запись в одной транзакции. Первичный ключ `team_id` защищает от двух текущих матчей. Проверка повтора создания предшествует проверке активности. При закрытии состояние матча и удаление активного участия обновляются атомарно. Историческая запись матча сохраняется для повторов и ответа `410`. Только обычный участник освобождает своё место через `leave`. Организатор освобождает свой текущий матч через `close`.

## 3. Форма, список и лобби

**Файлы** — `src/App.tsx`, `src/matches/*`.

Новая вкладка с URL лобби открывает тот же матч. Отмена формы оставляет список прежним. Ожидаемый начальный результат — сценарии блокируются на заглушках.
