# План реализации подготовки алгоритмов и онлайн-матчей Snake Arena

> **Для исполнителя:** использовать superpowers:executing-plans либо
> superpowers:subagent-driven-development после согласования спецификации.
> Коммиты создавать только по запросу пользователя.

**Статус** — согласован перед реализацией. Изменения интерфейсов по ходу работы
зафиксированы в [архитектуре](../../architecture.md) и [контракте](../../contracts/algorithm.md).

**Цель** — подготовить, проверить и выбрать версию Python-алгоритма по таймеру
лобби и автоматически разыграть онлайн-матч выбранными версиями.

**Архитектура** — один серверный движок рассчитывает новые онлайн-матчи
и тренировочные прогоны. Один контейнер исполняет весь пользовательский Python.
SQLite хранит отправки, выбор, дедлайн, состояние раунда и тренировочные карты.

**Стек** — React, TypeScript, Vite, FastAPI, SQLModel, SQLite, pytest.
Для редактора предлагается CodeMirror с режимом Python, для локального
исполнителя — один общий контейнер Python из спецификации.

**Спецификация** — [Подготовка алгоритмов и онлайн-матчи](../specs/2026-11-19-algorithm-matches-design.md).

## Общие ограничения

- Новые таблицы добавляются без изменения существующих записей онлайн-матчей.
- Все решения получают снимок до изменения состояния. Движок принимает
  направления и не запускает пользовательский код.
- Русский текст интерфейса, ошибок, справки и комментариев. Английские имена
  файлов и идентификаторы.
- Каждый этап проверяется отдельно. В изменениях кода выполняются ESLint,
  сборка, проверки форматирования затронутых частей и backend-тесты.

## Порядок работ

### 1. Тренировочный движок и контракт

**Файлы** — `backend/training/{state,engine}.py`,
`backend/tests/test_training_engine.py`, `docs/contracts/algorithm.md`.

**Интерфейсы** — `build_observation(state: ArenaState, snake_id: int) -> Observation`,
`advance(state: ArenaState, directions: Mapping[int, Direction]) -> ArenaState`.
Снимок включает итог при финише. Память и ошибки исполнения остаются в сессии
прогона. API отображения выделяет публичные данные для UI.

- [ ] Написать тесты на общую цель, обмен головами, собственное тело, освобождение
  своего и чужого хвоста, удержание хвоста при росте и каскад при гибели владельца
  хвоста. Проверить одинаковый итог на входе с переставленными участниками.
- [ ] Проверить тестами вход в воду, середину шага, запрет поворота, сухой выход,
  встречное движение и конкуренцию с участником, чей водный шаг уже начался.
- [ ] Проверить очки 10/30, яд при длинах 6/3/2, удержание хвоста при полушаге,
  расход и истечение щита, приоритет выжившего, ничью и отсутствие победителя.
- [ ] Запустить новый набор и убедиться, что тесты падают из-за отсутствия реализации.
- [ ] Реализовать снимок, вычисление намерений, разрешение конфликтов,
  применение объектов и формирование результатов. Описать все поля и примеры
  наблюдения, включая водный полушаг, в контракте.
- [ ] Выполнить `uv run --project backend --locked python -m pytest backend/tests`.

### 2. Генерация, повторяемость и стандартные боты

**Файлы** — `backend/training/{maps,bots}.py`,
`backend/tests/test_training_maps.py`, `backend/tests/test_training_bots.py`.

**Интерфейсы** — `generate_map(config: ArenaConfig, seed: int) -> ArenaMap`,
вариант `generate_map(config, seed, empty=True)` для очистки и
`decide_bot(bot: BotKind, state: Observation, seed: int) -> Direction`.
Моментальный снимок карты становится начальным состоянием прогона.

- [ ] Зафиксировать тестами одинаковую карту при том же seed, совпадение стартов
  при повторном запуске, копирование исходной карты, отсутствие пересечений
  и свободный первый ход. Проверить прямоугольное поле, максимальное
  заполнение, превышение вместимости и отсутствие появления еды после очистки.
- [ ] Добавить карты и детерминированное восполнение еды. Для каждой партии
  зафиксировать seed, стартовый снимок и параметры восполнения. Привязать
  восполнение к завершённым тактам; проверить нехватку свободных клеток.
- [ ] Проверить, что Random Bot возвращает допустимый поворот, Food Hunter
  идёт к ближайшей доступной еде и обходит очевидную стену, Pathfinding Bot
  находит обход с BFS, Survival Bot выбирает ход в более просторную область.
  Для всех проверить единственное допустимое направление на водном полушаге.
- [ ] Реализовать ботов над общим наблюдением с воспроизводимым выбором
  при равенстве оценок.
- [ ] Выполнить `uv run --project backend --locked python -m pytest backend/tests`.

### 3. Исполнитель Python и проверка исходника

**Файлы** — `backend/training/executor.py`,
`backend/training/worker.py`, `backend/training/Dockerfile`,
`backend/tests/test_training_executor.py`, `README.md`.

**Интерфейсы** — асинхронные `Executor.ready()`,
`Executor.decide(source, observation, memory, online=...)` и
`Executor.bot(kind, observation, seed)`. Каждый запрос имеет отдельный
воркер, поэтому сессия исполнения на сервере не требуется. Ошибка содержит
категорию, сообщение и номер строки при наличии.

- [ ] Написать тесты на синтаксис, отсутствие `decide`, исключение внутри вызова,
  некорректную форму, запрещённый поворот, не-JSON значения и превышение лимита
  памяти. Проверить возврат памяти следующим вызовом и раздельность сессий.
- [ ] Прогнать тесты с подменой транспорта до реализации адаптера, затем
  реализовать протокол и структурированные ошибки. Проверить ограничения на
  вход и выход до разбора. Воспроизвести те же проверки с реальным исполнителем и двумя независимыми воркерами в одном контейнере.
- [ ] Проверить реальный таймаут на бесконечном цикле, освобождение ресурсов,
  доставку следующего корректного запроса и недоступность исполнителя.
  Подтвердить конфигурацию изоляции и лимиты на целевом окружении. Проверить,
  что остановка одного воркера не останавливает контейнер или второй вызов.
  Проверить приоритет онлайн-тактов под нагрузкой тренировок.
- [ ] Документировать запуск исполнителя и категории ошибок. Зафиксировать
  подтверждённые ограничения в контракте и выполнить backend-тесты.

### 4. API тренировочных карт, проверки и прогонов

**Файлы** — `backend/models.py`, `backend/main.py`,
`backend/training/{api,runs}.py`, `backend/tests/test_training_api.py`.

**Интерфейсы** — под `/api/training` список, создание и изменение
`/maps`, подготовка карты через `POST /maps/generate` и
`POST /maps/clear`, проверка `POST /validate`, создание `POST /runs`,
чтение `GET /runs/{id}`, шаг `POST /runs/{id}/step` и остановка
`DELETE /runs/{id}`. Старт принимает карту и исходник. Шаг принимает
`expected_tick`; несовпадение возвращает 409 без повторного хода.
Предложение для первой версии — запуск шагов клиентом, максимум один
запрос одновременно. Скорость меняет расписание клиента. Пауза прекращает
планирование и дожидается ответа на уже начатый шаг.

- [ ] Проверить доступ владельца, отсутствие доступа гостя и другой команды,
  проверку Origin, сохранение карты после перезапуска сервера.
- [ ] Проверить гонку двух шагов, повтор запроса после потери ответа,
  невозможность шага после финиша, неизменность карты и версии кода во время
  прогона. Проверить fallback при ошибке `decide` и отсутствие хода при ошибке
  инфраструктуры.
- [ ] Реализовать хранение и API с существующими сессиями. Сериализовать шаги
  на уровне конкретного прогона, ожидать решения вне транзакции SQLite.
  Запускать решения от снимка одного такта и обновлять состояние один раз.
  Завершать исполнителей при финише, явном завершении и истечении срока
  неактивности. При ошибке сети получать текущий снимок и сверять номер такта.
- [ ] Выполнить весь набор backend-тестов, включая действующие онлайн-матчи.

### 5. Подготовка в лобби, версии и запуск онлайн-матча

**Файлы** — `backend/{models,matches,match_socket}.py`,
`backend/training/{state,engine}.py`, `backend/tests/test_matches.py`,
`backend/tests/test_match_preparation.py`.

**Интерфейсы** — новый статус `preparing`, команда организатора
`start_preparation` с `preparation_minutes`, снимок лобби
с `preparation_ends_at` и серверным временем. Команды участника
`submit_version`, `rename_version`, `select_version`; приватный список
версий в снимке участника. Отдельные таблицы хранят подготовку, версии
и зафиксированный состав с версией по каждой команде.

- [ ] Проверить роли, фиксацию состава, сроки, нумерацию и доступность исходника
  только владельцу. Проверить что смена имени и новая отправка сохраняют
  выбранный исходник. Проверить отметку времени и конкурирующие отправки.
- [ ] Проверить выбор до/ровно на/после дедлайна, рестарт до и после дедлайна,
  однократную фиксацию выбранных версий и доступ к итогу у всех команд.
  Без явного выбора должна использоваться последняя отправленная версия.
  Без отправок команда получает статус «Алгоритм не отправлен» и пропускает
  раунд. Проверить независимость тренировочных шагов.
- [ ] Реализовать переходы лобби и атомарную фиксацию версии при дедлайне.
  При повторных сетевых запросах на отправку использовать идентификатор
  операции, чтобы повтор не порождал дубликат.
- [ ] Подключить общий движок и контейнер к новым онлайн-раундам.
  Читать состояние, получить решения всех участников вне транзакции SQLite,
  затем зафиксировать следующий такт только при совпадении состояния раунда.
  Отмена или устаревший ответ исполнителя не должны менять итог.
- [ ] Проверить возобновление онлайн-матча с памятью каждого алгоритма,
  восстановление при недоступности исполнителя и поддержку старых снимков.
  Выполнить весь набор backend-тестов.
