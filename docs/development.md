# Правила разработки

## Общее

- При просьбе провести ревью, запускать агента .codex/agents/reviewer.toml

## Использование скилла ub-mode

Когда использовать:

- При внесении средних-крупных изменений в проект
- При работе со сложными, большими функциями с непростой логикой

## При работе с интерфейсом

После создания, изменения или удаления элементов интерфейса провести небольшую
проверку через agent-browser:

- Открыть затронутые экраны при десктопном размере окна.
- Визуально проверить вёрстку, читаемость, отступы, отсутствие наложений и
  обрезанного содержимого, соответствие существующему дизайну.
- Проверить основные взаимодействия и состояния, которых касается изменение.
- Провести [тест на юзабилити](development.md#проверка-на-юзабилити)
- Если обнаружены проблемы, исправить их и повторите проверку.
- В итоговом ответе сообщить, что проверено визуально и что не удалось проверить.

### Проверка на юзабилити

- Понятность: по экрану ясно, что пользователь может сделать и какой следующий шаг ожидается; названия кнопок
  соответствуют их действию.
- Обратная связь: после действия понятно, что произошло — операция выполняется, завершилась или произошла ошибка.
- Ошибки и ввод: сообщения помогают понять, как исправить проблему; подписи полей и требования к вводу видны до отправки
  формы.
- Навигация: понятно, где находится пользователь и как вернуться назад или отменить действие.
- Управление: основные действия доступны с клавиатуры, порядок перехода по Tab логичен, фокус виден.
- Читаемость: текст, элементы управления и состояния различимы; важная информация не передаётся только цветом.

## Тестирование

- Выбирать проверки по риску и характеру изменения, а не по количеству изменённых строк.
  Не требовать теста на каждое изменение или произвольного процента покрытия.
- Писать тесты для значимых правил и сценариев, сложной логики, важных граничных
  случаев и исправлений, где проверка помогает предотвратить повторение ошибки.
- Проверять наблюдаемое поведение и результат на подходящем уровне: отдельная функция,
  взаимодействие компонентов или полный сценарий. Использовать понятные примеры и названия,
  чтобы при падении теста было ясно, какое требование нарушено.
- Не писать тесты, повторяющие реализацию, проверяющие тривиальности, дублирующие другие
  проверки или зависящие от внутренних деталей, которые не входят в требуемое поведение.
- Для простых, обратимых и малорисковых изменений новый тест может быть не нужен,
  если достаточно существующих проверок или ручной проверки. Решение обосновывать тем,
  какой риск покрывает тест и какую пользу он приносит.
- При изменении требований пересматривать существующие тесты: обновлять или удалять те,
  которые закрепляют устаревшее поведение. Не добавлять отдельный регрессионный тест
  только ради проверки, что старая логика больше не возвращается; проверять новое
  поведение, если оно само по себе заслуживает теста.
- Регрессионный тест полезен при исправлении ошибки, если воспроизводит значимый сбой
  и проверяет ожидаемое поведение. Само название «регрессионный» не служит основанием
  для добавления теста.
- Если новый тест не добавлен, выполнять подходящие существующие автоматические
  и ручные проверки; в итоговом ответе указывать, что проверено, что не проверено и почему.
  При изменении кода обязательны `npm run lint` и `npm run build`.
- Во frontend тестовый раннер пока не настроен. Для backend используется pytest:
  `uv run --project backend --locked python -m pytest backend/tests`.
